# Architecture and trust boundaries

The browser reads a user-selected JSON-RPC endpoint, builds a restricted protocol call locally, asks the user's EIP-1193 wallet to sign/send, then checks the receipt and relevant resulting state. The static server stores no keys and has no application API. EIP-6963 discovery handles multiple wallet extensions without choosing whichever extension overwrote `window.ethereum` last.

`src/core/inspect.ts` reads Safe owners, threshold, nonce, modules, guards and canonical singleton runtime at a pinned block. Recovery modules are accepted only when their runtime matches the known deployed version after normalizing the immutable delay. The observed delay is shown to the user; it is never substituted with a product default.

`actions.ts` builds ordinary Safe CALL operations and restricted MultiSendCallOnly batches. A threshold-1 owner can execute with a prevalidated sender signature; multi-owner EIP-712 signatures bind the nonce, destination, value, calldata, operation, gas and refund fields. Other owners can approve the exact Safe hash on-chain. Simulation and gas estimation happen before broadcast; state is rechecked before sending. A review is not a transaction and simulation cannot reserve future chain state. Safe internal execution events are checked independently of the outer receipt status. ERC-20 Transfer logs and balance changes verify expected receipts; native receipts use balance changes, which cannot prove attribution against concurrent external transfers.

Guardian approvals use `multiConfirmRecovery` with a nonce-bound EIP-712 signature. The deployed module's legacy `confirmRecovery` ABI has four arguments and does not bind a nonce; the tool does not use it. Recovery approval, initiation and finalization are separate transactions. Finalization checks owners, threshold and cleared recovery state.

`card.ts` recognizes EIP-1167 clones of the documented Gnosis Pay Delay implementations and validates avatar, target and enabled controller. The Picnic Safe queues a transaction as the enabled module. Queue events are reconstructed and matched against stored hashes. Dispatch is permissionless, but only decodable native/ERC-20 transfer calls are executable here. Delegatecall and arbitrary unknown queue entries are refused. Contract cooldown/expiry controls execution; the browser rechecks the queue head before submission. Concurrent miners can still change a queue after the wallet signs.

`investments.ts`, `mamo.ts`, and `legacy-routes.ts` contain exits only. Historical basket bridges run in the NFT wallet's context through `withdrawPortfolio`; the connected Safe must own the NFT. LP routes require explicit minimum outputs, and protocol simulation can reject stale liquidity. Harvest/Balancer/Jarvis output metadata is resolved on-chain when inspected. The tool never treats a failed read as a zero balance.

`progress.ts` imports only a small versioned schema: chain/address labels, transaction hashes, status, and public receipt expectations. It strips unknown fields, validates addresses and caps file size. No RPC URL or signatures are exported. Hashes are persisted immediately after the wallet returns them, before confirmation waiting. A provider that broadcasts but throws before returning a hash remains an unavoidable ambiguous-submission case: inspect wallet activity before repeating.

Builds are static Vite assets with relative paths. The packaged archive has deterministic tar metadata, SHA-256 checksums for every included file and the source commit in `BUILD.json`. Rebuild from the lockfile and compare checksums; hosting is optional.

## Automatic diagnosis and three-step flow

Step 0 starts automatically when an external wallet connects through the step-0 ConnectKit button (the only place it appears). The inspected account is read-only and follows connected-account discovery. Saved-account navigation is removed; progress import/export remains. Address changes clear active inspection and transaction review. Changes received while an action is busy are applied after it settles. All ten configured networks run independently and publish incremental results. Changing the address or RPC configuration cancels stale results and further batches; in-flight RPC calls are bounded by their attempt’s transport timeout. Diagnosis continues while the user opens a result in steps 1–3. Opening a result carries its network into subsequent reviews; it does not request a wallet network switch.

`diagnosis.ts` verifies RPC chain identity and inspects the account before scanning native balance, local token balances, known investment positions (including pending requests with zero shares), Polygon basket ownership and Base MAMO discovery. Token balance reads use the account snapshot block and direct Multicall3 `aggregate3` chunks of 100 where available (small direct-read groups elsewhere). viem's `multicall({ allowFailure })` is not used for the scan because it folds a whole-request HTTP 429 or timeout into per-token failures. Chunks halve on oversized/failed requests down to 12 tokens, then fall back to individual reads; already-found holdings are kept. A contract that itself reverts `balanceOf` is listed as unreadable (the network answered; the balance is unknown), separately from tokens the RPC did not answer, which make the scan partial. If an RPC no longer serves the snapshot block's state (short-history BSC nodes), token chunks re-pin to a newer block and the UI shows the block range used. Found token decimals are verified on-chain in batches. RPC/contract failures remain partial, unavailable or unreadable, never empty balances.

Reads go through `reads.ts`: without a custom RPC, Ethereum and BSC may fail over between documented public endpoints (BSC starts with `bsc-dataseed.bnbchain.org`, listed in BNB Chain's JSON-RPC docs, because viem's thirdweb default returns HTTP 429 with multi-minute Retry-After). Every endpoint must report the expected chain ID before any of its answers are used, and the UI lists the hosts that answered. A custom RPC is used alone. Transactions never use fallback endpoints; they use the single selected RPC and verify its chain. Users may add an ERC-20 by network and contract address for the session: code, balance and decimals are read from one endpoint at one block, metadata strings are sanitised and rendered as text, a missing `decimals()` leaves raw units, and pending reads are cancelled when the account or RPC changes. Network marks are bundled (ConnectKit inline SVGs; local monograms for HyperEVM and Robinhood Chain); no remote icon is loaded. The local catalogue is not universal, and basket contents, separate card/controller addresses and assets absent from the catalogue still need further inspection. Connected-wallet gas is separate from the account's asset balance; each transaction still rechecks state and estimates gas.

`src/catalog/tokens.json` contains 9,578 deduplicated public token entries derived from Picnic `common/assets-v2.json` at commit `e0153e2e79fed487a1a6adbdb17d74685a58c7a7`, restricted to supported chains and augmented with Polygon token entries in the local legacy catalogue. Only chain ID, address, name, symbol and decimals are retained. Native tokens are checked separately. Catalogue metadata is not proof that a contract remains deployed or transferable.

The interface groups access recovery, sender/destination/gas preparation, and asset exits. ConnectKit upstream supplies the external-wallet modal (Picnic uses a fork of this same library); Wagmi discovers injected providers. The selected connector supplies the EIP-1193 provider to the existing signing functions. Changing wallet/account/network invalidates the transaction review. React 18 is pinned to match ConnectKit's supported peer range. WalletConnect QR relays are not configured; an installed wallet or wallet browser is required. No Picnic connector keys are reused.

`components/migration.ts` derives one row model from diagnosis results and custom tokens, used by the diagnosis table, the Prepare wallets checklist and the Move funds table. Row IDs are stable across rescans and RPC changes (`chain:native`, `chain:token:<address>`, `chain:position:<product>`, `chain:baskets:<NFT>`, `chain:mamo:<strategy>`, `100:card:<Safe>:<asset>`); product share tokens map to their position ID and custom tokens share the token namespace, so nothing is listed twice. Verified nonzero holdings and actionable pending requests are selectable. Unidentified basket counts retain a separate discovery row; they are never displayed as an invented token balance. The selection is scoped to the lowercased source account and reset when it changes. Until a network is edited, its undecided rows default to selected; editing a network freezes its current defaults first, and entering Move funds freezes all of them. Afterwards, newly found rows arrive unselected and flagged as new, and manually unticked rows stay unticked across rescans. Move funds gates the table, positions, MAMO, legacy baskets and the manual transfer form on explicit exclusion, so a network briefly emptied by a post-transaction rescan keeps its committed choices. The selected rows are the only inputs admitted to batch planning or individual withdrawals.

Native balance checks happen only in Prepare wallets, automatically and in parallel for selected networks whose owner check passes, and are scoped to chain, RPC, inspected account and connected sender. Each result is applied only if its context key and request number are still current, so a late answer for a previous wallet, RPC or account, or a superseded refresh, is discarded. They show a block number, not a guaranteed future gas budget. Recovery approvals/start/finalization need gas before the preparation step too. Direct Safe execution charges the external transaction sender; the Safe/card need no separate gas deposit for this path. EOA native withdrawals must retain gas.

The demo provider is announced through EIP-6963 only in local Vite development with `?demo=1`. It is selected through the same ConnectKit modal and Wagmi connector as installed wallets, and never overrides the browser's wallet. Its RPC verifies local Anvil before serving requests.

Transitive `decode-uri-component` and older `uuid` releases are overridden to patched versions to keep the connector dependency tree free of known audit findings. Only injected connectors are configured; relay/mobile SDK connector paths are not enabled or claimed as tested.

The automatic catalogue excludes Ethereum VZZN (`0x60867B79a68AbECB78351B2dbB5fdec4282C5aCB`), whose ERC-20 reads reverted in the verified probes. It can still be entered explicitly as a custom token; failed reads remain unknown, never zero.

Passkey UI classification checks owner bytecode at the account snapshot block against Picnic Safe WebAuthn proxy runtimes v0.2.0/v0.2.1, masking constructor immutables and checking the embedded canonical singleton. This is UI classification only, never transaction authorization. Other contract signers, unavailable owner reads and unrecognized/shared-signer implementations are unknown; a recovery module alone is not taken as proof of a passkey. EOAs and ordinary Safe owners do not show the recovery sub-step. Gas-payer balances are read only by Prepare wallets; native asset inventory is still read during diagnosis.

The migration UI requires a receiving wallet different from the connected signing wallet. `core/destination.ts` validates this in preparation, manual transfer/card requests, investment destinations, transaction review and execution. This product rule is distinct from Candide's contract restriction that a proposed new Safe owner cannot be a configured guardian; `recoveryAction` already rejects that before approval/start. Removing the connected-wallet destination shortcut must not relax that recovery check.

All three asset views use the same flat row model. Clicking a Move funds row opens only that position, card asset or NFT; there is no category navigation. Product positions are refreshed individually, and identified NFT IDs and token contracts are fixed in their detail forms. Card queues have their own pending row. Separate card Safe addresses are added for this session, checked against the inspected controlling account through the known v5 Delay module, then scanned on Gnosis. Child scans are cancelled on account/RPC changes, merged only into their controller context and re-run on refresh. A lost controller relationship is disclosed and prevents those rows from being selected. Polygon basket discovery reads ownerOf through aggregate3 batches of 200 at the ownership-count snapshot block, stopping when the verified IDs match balanceOf. Up to 100,000 IDs are scanned; limits/count mismatches remain explicit. Burned IDs may revert without implying a transport failure. Successful chunks are reused when retrying missing ownership reads. MAMO strategy addresses are retained instead of collapsing verified positions into a count.

`core/discovery.ts` derives the original Picnic Safe (EOA owner, nonce zero, pinned factory/singleton/module setup) and verifies deployed singleton/runtime and current ownership on Gnosis before `useConnectedAccount` selects it. This distinguishes the connected signer from the account holding assets; the source remains read-only and follows the connected signer. Switching wallet/RPC cancels stale resolution, and diagnosis cannot continue while it is pending. An absent predicted contract leaves the EOA selected; a failed verification is disclosed. This route does not claim general/passkey Safe enumeration.

Card discovery independently queries the original deterministic Gnosis Pay address and incoming/outgoing ERC-20 transfer counterparties of the controller, plus outgoing transfers of the original card. Incoming transfers matter for migrated cards that have withdrawn to the controller but were never directly funded by it. Up to 2,000 newest logs per query and 64 candidate addresses are inspected, with limits/errors disclosed. Candidate proxies are screened by singleton then validated through `inspectCard`; transfer history alone never authorizes a card. Only cards with a verified v5 Delay and matching controller enter the existing session scan/selection flow automatically, and fresh controller/queue checks still happen before review. Discovery is JSON-RPC only: neither Picnic/Mongo, the Gnosis Pay API nor Safe Transaction Service is a runtime dependency. Migrated cards with no matching transfer evidence and custom deployments still need the explicit address fallback.

ReadPool retries a transiently failing read unit at most twice, using per-request timeouts of 20, 40 and 60 seconds and bounded backoff/failover. Successful diagnosis units, batches and other networks are never restarted by automatic retry. Multi-request account snapshots repeat together to preserve their consistency. Chain identity is verified for each endpoint before its data is used. Reverts and deterministic validation failures are not retried; stale state and oversized payloads retain their separate repin/split paths. An exhausted transport failure is not split into a second retry tree. A sole RPC asking for a cooldown longer than the bounded backoff is left unverified. Concurrent retry progress is exposed to the scan UI and cleared on completion; cancellation suppresses stale output. Missing token precision keeps the result partial and the amount in raw units. Refresh diagnosis still deliberately refreshes all selected network data.

Card admission (automatic and manually added) and asset rows require the v5 Delay implementation. The deterministic original card remains only a history hint when it is v4; its old balances and queue are not admitted. The fresh check before opening a card withdrawal also requires v5. `delayVersion` describes the verified Delay implementation, not a claim that every other account-kit module has been version-classified.

The Needs attention retry button resumes only the selected network’s missing units. `ReadCheckpoint` holds successful reads in session memory, namespaced by chain/RPC/account; it is cleared for account/RPC changes and full refresh. Account snapshots, positions, token batches/precision, strategy registry/positions, basket pages and card-discovery queries are checkpointed. Successful token reads retain their original block when a later chunk re-pins. During resume, the view merges already-confirmed holdings until the completed diagnosis replaces it. Failed reads are not cached and receive the bounded 20/40/60-second attempts again; known contract failures are not presented as temporary RPC failures. Previously completed child card scans and other networks are untouched. No transaction uses the checkpoint.

The old deterministic card is a discovery hint. A verified unsupported singleton there is recorded under informational notes, not as an incomplete v5 scan; actual candidate/history RPC failures still remain pending. The live v5 card must still pass singleton/Delay/controller checks.

`LinkedAccounts` presents the connected signer, the automatically identified Picnic Safe and verified v5 child card Safes in one read-only component. Only the signer row has the ConnectKit control. The Picnic label requires automatic account identification, and the card label requires the current v5 Delay/controller relationship; unrelated/unverified saved targets use a generic inspected-account label. Duplicate account addresses are not repeated, and the prior detached automatic-identification notice is removed.

## Batch migration

`core/multisend.ts` pins Safe MultiSendCallOnly 1.4.1/1.3.0 deployments (address, runtime keccak and chain list from the Safe deployments registry, `src/catalog/multisend.json`). Packing is `uint8 operation (always 0) · address · uint256 value · uint256 length · bytes`. `assertBatchPayload` decodes the payload and requires exactly the reviewed CALL children, no Safe-level value, and no child calling the Safe or a multisend; `verifyMultiSendRuntime` checks the deployed runtime hash at the selected RPC before sending. `PreparedAction.operation` (default 0) is included in `getTransactionHash`, the EIP-712 message and `execTransaction` calldata; DELEGATECALL is accepted only for such a batch. Direct `eth_call` of the inner call is skipped for batches; the full Safe execution is simulated and estimated instead.

`core/batch.ts` turns the selected rows of one network into fresh facts (`readBatchFacts`; token and basket reads use the review snapshot block, while protocol inspectors refresh their own state) and then, purely, into one entry per selected asset (`planBatch`): included (with outcome received / shares / queued), individual, later or empty. Card queueing is refused while the card already has pending requests. `batchPartAction` builds the Safe action with all expected receipts and queued hashes; revalidation re-reads facts and requires every relied-upon amount to be unchanged or larger. Receipt expectations (`receives`, `native`, `queued`, `operation`, `multisend`, `calls`) are persisted with the pending transaction and validated on import; `verifyReceipt` is shared by the immediate wait and the later receipt check. Native batch transfers have no log and are proven by `ExecutionSuccess` of the exact Safe hash.

`core/basket-contents.ts` reads a basket wallet against a deduplicated plan derived from the legacy catalogue: one `balanceOf` per ERC-20 contract, one stake read per Autofarm/MasterChef pool, and native POL via Multicall3 `getEthBalance`. `components/useBasketContents.ts` queues every identified basket (two concurrently, prioritised when opened/reviewed), checkpoints chunks and resets only for an account or Polygon RPC change. `BasketContentsView` is the single presentation used in diagnosis, Prepare wallets, Move funds and the batch review.

`core/destination.ts` collects guardians from every snapshot of the current source (any network) and rejects them as destinations and as recovery new owners; `sendAction` re-reads the source Safe's guardians, including queued card destinations, before sending.

## Wallet confirmation flow

The network migration button performs fresh planning and simulation and then calls the selected connector's EIP-1193 provider in the same explicit user action. No review checkbox or second app confirmation gates the wallet request. Single-action protocol forms follow the same rule; their prepared transaction remains visible for a retry only if the wallet request fails or is declined. Busy refs prevent duplicate clicks, context changes invalidate in-flight plans, and pending submitted hashes still block resubmission. The selected sender is bound to a batch before execution.

`connectedWallet` reads the already authorized accounts with `eth_accounts` rather than asking for connection permission again. It uses only the provider supplied by the selected connector, with automatic wallet-request retries disabled. Progress distinguishes connection, network switch, validation, simulation, wallet confirmation and receipt waiting. Error -32002 directs the user to the request already open in the extension. EIP-6963 discovery keeps selected providers independent of another extension's read-only `window.ethereum`.
